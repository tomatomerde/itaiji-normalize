# mj-shrink-map

[English README is here](./README.md)

IPA の**MJ縮退マップ**(ハードコード辞書ではなく公的データ)を根拠とする、
日本語異体字の縮退変換・等価判定・名寄せキー生成ライブラリ。

依存ゼロ。全データを同梱し、ビルド時・実行時とも外部ネットワークへアクセス
しない。Node.js 18+ は、公開する tarball を Node 18 に install して
`require()` と `import()` の両方を実行する CI ジョブで実証済み。ブラウザと
Cloudflare Workers は対応対象だが CI では未検証([既知の制約](#既知の制約)参照)。

## なぜ作ったか

日本語の人名・地名には異体字(﨑/崎、髙/高、邊/邉/辺 など)が多く、素朴な
文字列一致では名寄せが崩れる。既存の代表的な選択肢である npm `itaiji` は、
根拠の明記がない約1,400件の手作り辞書(旧字→新字の一方向)で、IVS(異体字
セレクタ)にも対応していない。

本パッケージは代わりに MJ縮退マップ(文字情報技術促進協議会/IPA が公開する
データセット)から構築する。このデータは、文字同士の対応関係に「戸籍法関連
通達」「法務省告示582号別表第四」「JIS包摂規準」「辞書類」「読み・字形によ
る類推」といった根拠区分を明記している。実装前調査では、`itaiji` 辞書と比
べて**約19倍の異なり文字対応**をカバーし、`itaiji` には存在しない IVS 対応
も持つことを確認した。詳細な数値は
[`docs/phase0-report.md`](./docs/phase0-report.md) を参照。

**`itaiji` の完全な代替ではない。** MJ縮退マップは「JIS X 0213 で表現可能
な字への縮退」であり、新字体への正規化ではない。`itaiji` の1,404組のうち
約86%は本ライブラリの等価関係でカバーできるが、両字ともすでに独立して
JIS表現可能なペア(啞→唖、鷗→鴎 等)は、どちらも縮退の必要がないため
「縮退」の対象にならない。旧字体→新字体の一方向置換が目的なら、この違いが
自分のユースケースに影響するか確認してほしい。

```sh
npm install mj-shrink-map
```

## API

```ts
import { reduce, isVariant, getVariants, toMatchingKey } from "mj-shrink-map";

reduce("﨑");
// {
//   input: "﨑",
//   candidates: [
//     { char: "崎", basis: ["family-register-notice"] },
//     { char: "﨑", basis: ["jis-inclusion-rule"] },
//   ],
//   unique: "崎",
//   resolvedVia: "base",
// }

isVariant("﨑", "崎"); // true
isVariant("崎", "高"); // false

getVariants("崎");
// 5件。順序に意味はない: 㟢 嵜 陭 﨑 𡼋
// [{ char: "㟢", basis: [...] }, { char: "嵜", basis: [...] }, ...]

toMatchingKey("田中﨑");
// { key: "田中崎", unresolved: [] }
```

### `reduce(char): ReduceResult`

1文字(異体字セレクタが後続する場合は基底文字+セレクタの1単位)を受け取り、
記録されている JIS X 0213 表現可能な候補すべてを、根拠区分(`basis`)付きで
返す。

`char` が文字列でない場合、またはちょうど1単位でない場合は `TypeError` を
投げる。意図的な仕様で、長い文字列の先頭だけを黙って処理したり、名前の配列を
1つの名前のように受理したりすると、もっともらしい誤出力として不具合が隠れる
ため。異体字セレクタが2つ以上付いた入力も同じ理由で拒否する(1つ目だけを
使えば残りを捨てることになる)。文字列全体には `toMatchingKey` を使う。

`unique` は代表字の一意選択結果で、候補がゼロの場合、または選択アルゴリズ
ムの下で複数候補が拮抗し一意選択が恣意的になる場合は `null` を返す。選択ヒ
ューリスティックは次の優先順位: まず法務省告示582号別表第四に記録された順
位を優先し、次に戸籍法関連通達のホップ数が最小のものを優先し、それでも決
まらなければ(コードポイント順など)恣意的に選ばず `null` を返す。これは
[`src/reduce.ts`](./src/reduce.ts) に記載した独自のヒューリスティックであ
り、他ツールのアルゴリズムを移植したものではない。

`resolvedVia` は、どのテーブルエントリが引けたかを示す: 入力自身の変異
シーケンスが見つかれば `"ivs"` / `"svs"`、素の基底文字にフォールバックした
(またはセレクタが無かった)場合は `"base"`、何も見つからなければ `"none"`。
IVS 固有の結果とフォールバックを区別できる唯一の手段。

なお `reduce` は関係を**1段階だけ**進める。安定する字に達するまで複数段階を
要する文字が多いため、名寄せキーには不動点まで反復する `toMatchingKey` を使う。

### `isVariant(a, b): boolean`

`a` と `b` が MJ の異体字グラフ上で直接連結しているかを判定する: 一方が他
方に縮退する関係、または両者が同一 MJ 字形の縮退候補同士である場合に true
を返す。これは**直接関係**であり、グラフ全体の推移閉包ではない。一部の根拠
区分(辞書類、読み・字形による類推)は連鎖して大きな連結成分を作るため、推
移閉包にすると本来別の文字同士を過剰に同一視してしまう。実測した連結成分の
規模は [`docs/phase0-report.md`](./docs/phase0-report.md) #6 を参照。

### `getVariants(char): Candidate[]`

`char` と直接関係にある文字を根拠付きですべて列挙する(直接関係の定義は
`isVariant` と同じ)。順序に意味はない。検索クエリ展開(「崎」で「﨑」も
ヒットさせる)などに使う。

### `toMatchingKey(text, options?): { key, unresolved }`

`text` の各文字を、自分自身に縮退する安定した代表字に達するまで**繰り返し**
縮退して名寄せキーを生成する(1段階では足りない文字が大半のため)。解決でき
なかった文字は `key` 中で元の文字のまま残し、`unresolved` に(正規化後の)
文字列中の位置とともに記録する。黙って推測することはしない。

`reason` は次のいずれか:

| reason | 意味 |
| --- | --- |
| `"no-candidate"` | MJ縮退マップにエントリが存在しない |
| `"ambiguous"` | 候補が拮抗して一意選択できない(連鎖の途中で起きた場合も含む) |
| `"cycle"` | 各段階は一意なのに連鎖が循環して安定しない(例: 址 と 阯 は互いに縮退する) |
| `"unsupported-sequence"` | 変異セレクタが2つ以上付いていたため、縮退せず素通しした |

**`unresolved` に載るのは漢字だけ。** かな・英数字・記号・空白は定義上 MJ
文字集合の対象外であり、これらを載せると本当の情報が埋もれてしまう。実際、
住所1行で34文字中33文字が `unresolved` に載り、`if (result.unresolved.length)`
という自然な呼び出し側チェックがほぼ全入力で発火していた。漢字以外も `key`
には元のまま入る。

`options.unicodeNormalize` の既定値は `"NFKC"`。実装前調査で、CJK互換漢字
474字中460字が NFKC/NFC で統合漢字に分解されることを確認したため、MJ 変換
の前に正規化しておくことでこれらを無料でカバーできる。正規化で吸収されず安
定して残る文字(髙・邊・濵など著名な例を含む)こそが MJ テーブルの担当範
囲となる。`false` を渡すと MJ 側の寄与だけを分離して見ることができ、
`"NFC"` を渡すと互換漢字を区別したまま残せる。

## IVS 対応

MJ文字情報一覧表では、MJ図形名に IVS(異体字セレクタ、U+E0100–U+E01EF)や
SVS が付与されていることが多い(本パッケージのビルドに用いた版では約59,000件
中約11,000件で、生成される変異シーケンスのキーは 9,973 件)。
`reduce`・`isVariant`・`getVariants` はいずれも「基底文字+直後の異体字
セレクタ1つ」を1入力単位として受理する。該当するシーケンスが見つからない場合、
`reduce` は基底文字のエントリにフォールバックし、それを `resolvedVia: "base"`
で報告する。

SVS(標準異体字セレクタ)として受理するのは **U+FE00–U+FE0D のみ**。
U+FE0E と U+FE0F は Unicode が定める「テキスト/絵文字の**表示**セレクタ」で
あって異体字セレクタではなく、とりわけ U+FE0F は絵文字の一部として通常の
文章に頻出する。これを異体字セレクタとして扱うと黙って食い潰すことになる。
範囲を狭めても失うものは無い: MJ データが実際に使う SVS は U+FE00 と U+FE01
だけである。したがって `toMatchingKey("㊗️")` は U+FE0F を保持する。

副作用として知っておいてほしい点: U+FE0F が異体字セレクタでなくなったため、
`"崎️"` は1単位ではなく2文字になる。したがって単一文字を扱う関数
(`reduce`・`isVariant`・`getVariants`)は、これを黙って 崎 として扱わずに
例外を投げる。`toMatchingKey` は通常どおり処理する。

## 既知の制約

推定ではなく実測値。採用前に検討してほしい。

**バンドルサイズ。** テーブルは大きい。`esbuild --bundle --minify --format=esm`
で minify + gzip した概算値(バンドラとそのバージョンにより数 KB 前後する):

| import する対象 | gzip |
| --- | --- |
| `isVariant` のみ | 約 281 KB |
| `reduce` のみ | 約 270 KB |
| `toMatchingKey` | 約 271 KB |
| API 全体 | 約 552 KB |

生成テーブルには `/* @__PURE__ */` を付けてあり、使わないテーブルはバンドラが
削除できる(付ける前は全利用者が 552 KB を負担していた)。ただし API 全体を
使う場合は全額かかり、Cloudflare Workers の 1 MB(gzip)予算の半分以上を消費する。
テーブルのコンパクトな再符号化はロードマップにあり、未実装。

**`unicodeNormalize: "NFKC"`(既定)は漢字以外も畳む。** NFKC は互換正規化
なので、想定外の書き換えも起きる: `㈱`→`(株)`、`№`→`No`、`①②③`→`123`、
`㌢`→`センチ`、`ﬁ`→`fi`、`Ⅻ`→`XII`。名寄せでは通常望ましい挙動だが、
キーが入力より長くなることがある。入力の形を保ちたい場合は `"NFC"` か
`false` を渡す。

**full ICU が必要。** `String.prototype.normalize` は full ICU データを要する。
公式の Node.js ビルドは満たすが、`--with-intl=small-icu`(や `none`)で
ビルドされた Node では正しく正規化されない。その場合は
`unicodeNormalize: false` を使う。

**スループット。** 短い氏名で `toMatchingKey` およそ 50〜70 万回/秒(10万件で
約150〜210ms、計測した複数マシン、Node 22)。約束ではなくオーダーの目安として
扱ってほしい。呼び出しをまたぐキャッシュは意図的に持たない(隠れたグローバル
状態になるため)。数百万行を処理してさらに速度が必要なら、呼び出し側で文字単位に
メモ化してほしい。

**CI で未検証**: ブラウザおよび Cloudflare Workers 上での実行。Node は
18・20・22 を検証しており、18 については公開する tarball を install して
`require()` と `import()` の両方で呼び出している。

## FAQ: なぜ `reverse()` がないのか

MJ縮退マップは多対一の対応関係(複数の MJ 字形が同じ JIS 表現可能字に縮退
する)である。逆方向、つまり「この新字体から、元の旧字体を一意に求める」に
は、一般には唯一の正解が存在しない。実装前調査では、1つの縮退先に対して
4つ以上の異なる縮退元候補が見つかるケースがあり、多くの場合それ以上絞り込
む根拠がなかった。`reverse()` が黙って1つを選んでしまうと、もっともらしい
が根拠のない出力を生んでしまう。`getVariants()` で根拠付きの候補を列挙する
ので、選択は文脈(または人間の判断)を持つ呼び出し側で責任を持って行ってほ
しい。

## ロードマップ / v1 非対応

- ホスト型 API・Web サービス化はしない(あくまでライブラリ)
- 法務省の誤字俗字・正字一覧(民一2842号通達別表)は統合しない —
  `docs/phase0-report.md` #4 参照。この調査を行った環境にはネットワークア
  クセスがなく、機械可読性を確認できていない
- テーブルは素の JSON。コンパクトな再符号化(縮退先の共有辞書化、コード
  ポイント差分符号化)により API 全体のバンドルを現在の 552 KB(gzip)から
  大きく下げられる。実装前調査で設計済み・未実装
- ブラウザおよび Cloudflare Workers 上での実行は CI 未カバー
- Python版は未着手(TypeScript版の反応を見てから判断)
