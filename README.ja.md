IPA の**MJ縮退マップ**(ハードコード辞書ではなく公的データ)を根拠とする、
日本語異体字の縮退変換・等価判定・名寄せキー生成ライブラリ。

ネットワークへアクセスしない。(これらのランタイムはいずれもビルド成果物に対して
CI で実行検証している。詳細は[サポート範囲](#サポート範囲)。)

パッケージをそのままページ内で動かしている。入力しながら DevTools の Network を
見ると、読み込み後は1リクエストも出ていないことが確認できる。

## なぜ作ったか

日本語の人名・地名には異体字(﨑/崎、髙/高、邊/邉/辺 など)が多く、素朴な
文字列一致では名寄せが崩れる。既存の代表的な選択肢である npm `itaiji` は、
根拠の明記がない約1,400件の手作り辞書(旧字→新字の一方向)で、IVS(異体字
セレクタ)にも対応していない。

本パッケージは代わりに MJ縮退マップ(文字情報技術促進協議会/IPA が公開する
データセット)から構築する。このデータは、文字同士の対応関係に「戸籍法関連
通達」「法務省告示582号別表第四」「JIS包摂規準」「辞書類」「読み・字形によ
る類推」といった根拠区分を明記している。実装前調査では、`itaiji` 辞書と比
べて**約19倍の異なり文字対応**をカバーし、`itaiji` には存在しない IVS 対応
も持つことを確認した。詳細な数値は
[`docs/phase0-report.md`](./docs/phase0-report.md) を参照。

**`itaiji` の完全な代替ではない。** MJ縮退マップは「JIS X 0213 で表現可能
な字への縮退」であり、新字体への正規化ではない。`itaiji` の1,404組のうち
約86%は本ライブラリの等価関係でカバーできるが、両字ともすでに独立して
JIS表現可能なペア(啞→唖、鷗→鴎 等)は、どちらも縮退の必要がないため
「縮退」の対象にならない。旧字体→新字体の一方向置換が目的なら、この違いが
自分のユースケースに影響するか確認してほしい。

## インストール

```sh
npm install itaiji-normalize
```

導入前に知っておくべき条件が2点ある。どちらも install 時ではなく**入れたあとに**
効いてくるもの。詳細は[既知の制約](#既知の制約)。

- **同梱テーブルが大きい**: 単一エントリポイントでも gzip 約 280〜290 KB、
  **API 全体では約 570 KB**。Cloudflare Workers では 1 MB 予算の半分を超える。
  必要なものだけ import すること(テーブルには `/* @__PURE__ */` が付いており、
  使わない分はバンドラが落とせる)。
- **既定の `unicodeNormalize: "NFKC"` には full ICU が必要**。公式 Node ビルド・
  Chromium・workerd はいずれも持っているが、`--with-intl=small-icu` でビルドした
  Node は持たず、`unicodeNormalize: false` を渡さない限り異なるキーを生成する。

## 使用例

```ts
import { reduce, isVariant, getVariants, toMatchingKey } from "itaiji-normalize";

reduce("﨑");
// {
//   input: "﨑",
//   candidates: [
//     { char: "崎", basis: ["family-register-notice"] },
//     { char: "﨑", basis: ["jis-inclusion-rule"] },
//   ],
//   unique: "崎",
//   resolvedVia: "base",
// }

isVariant("﨑", "崎"); // true
isVariant("崎", "高"); // false

getVariants("崎");
// 5件。順序に意味はない: 㟢 嵜 陭 﨑 𡼋
// [{ char: "㟢", basis: [...] }, { char: "嵜", basis: [...] }, ...]

toMatchingKey("田中﨑");
// { key: "田中崎", normalized: "田中﨑", unresolved: [] }
```

## FAQ: なぜ `reverse()` がないのか

MJ縮退マップは多対一の対応関係(複数の MJ 字形が同じ JIS 表現可能字に縮退
する)である。逆方向、つまり「この新字体から、元の旧字体を一意に求める」に
は、一般には唯一の正解が存在しない。実装前調査では、1つの縮退先に対して
4つ以上の異なる縮退元候補が見つかるケースがあり、多くの場合それ以上絞り込
む根拠がなかった。`reverse()` が黙って1つを選んでしまうと、もっともらしい
が根拠のない出力を生んでしまう。`getVariants()` で根拠付きの候補を列挙する
ので、選択は文脈(または人間の判断)を持つ呼び出し側で責任を持って行ってほ
しい。

## サポート範囲

- 対応文字集合: MJ文字集合(戸籍統一文字+住基ネット統一文字、Ver.006.02 で
  約58,900字)のうち JIS X 0213 へ縮退可能なもので、縮退元 30,345 字・
  変異シーケンスキー 9,950 件。MJ に含まれない漢字(中国簡体字の 龟 等)は
  対象外で、`reduce`/`getVariants` は候補ゼロを返し、`toMatchingKey` は
  `"no-candidate"` として報告する。
- 曖昧さは常に明示する。複数候補・候補ゼロ・`unique` の判定不能はすべて明示
  的に表現され、勝手に解決しない。実測分布は
  [`docs/phase0-report.md`](./docs/phase0-report.md) を参照(MJ全エントリの
  約39%が縮退候補ゼロ、約49%が候補1つ、約12%が複数候補)。
- **免責**: 本パッケージは戸籍・法務・金融用途での同一性判断を保証しない。
  あくまでテキスト正規化の補助であり、法的な同一性の権威ではない。
- **バージョン `0.x`。API は変わりうる。** 個人プロジェクトであり、対応は
  ベストエフォートで行う。Issue や Pull Request は歓迎するが、応答時期は保証しない。
  本ソフトウェアは MIT ライセンスのとおり無保証(as is)で提供する。
- **上で対応を謳ったランタイムはすべて、ソースではなくビルド成果物に対して CI で
  実行検証している**: **Node.js 18+**(公開する tarball を Node 18 に install して
  `require()` と `import()` の両方で呼び出し、加えて Node 20・22 で全テスト)、
  **ブラウザ**(ESM バンドルを headless Chromium にモジュールスクリプトとして読み込み)、
  **Cloudflare Workers**(Workers が実際に使うランタイム workerd 上でバンドルを実行)。
  CI が覆っていない範囲は[既知の制約](#既知の制約)に挙げてある。

## 既知の制約

推定ではなく実測値。採用前に検討してほしい。

**バンドルサイズ。** テーブルは大きい。`esbuild --bundle --minify --format=esm`
で minify + gzip した概算値(バンドラとそのバージョンにより数 KB 前後する):

| import する対象 | gzip |
| --- | --- |
| `isVariant` のみ | 約 287 KB |
| `reduce` のみ | 約 282 KB |
| `toMatchingKey` | 約 282 KB |
| API 全体 | 約 568 KB |

0.1.3 で `reduce` と `toMatchingKey` がそれぞれ約11 KB増えた——[`reduce`](#reducechar-reduceresult)
で説明する常用漢字/人名用漢字タイブレークを支える `KANJI_POLICY` テーブル
(2,999件)を新たに取り込むため。`isVariant` はこのテーブルを参照しないので
ほぼ変化していない。API全体のバンドルは約6 KBしか増えていない——両関数を
まとめてバンドルすると、テーブルのコピーを1つだけ持てば済み、2重に払わずに
すむため。

生成テーブルには `/* @__PURE__ */` を付けてあり、使わないテーブルはバンドラが
削除できる(付ける前は全利用者が全テーブル分を負担していた)。ただし API 全体を
使う場合は全額かかり、Cloudflare Workers の 1 MB(gzip)予算の半分以上を消費する。
テーブルのコンパクトな再符号化はロードマップにあり、未実装。

**`unicodeNormalize: "NFKC"`(既定)は漢字以外も畳む。** NFKC は互換正規化
なので、想定外の書き換えも起きる: `㈱`→`(株)`、`№`→`No`、`①②③`→`123`、
`㌢`→`センチ`、`ﬁ`→`fi`、`Ⅻ`→`XII`。名寄せでは通常望ましい挙動だが、
キーが入力より長くなることがある。入力の形を保ちたい場合は `"NFC"` か
`false` を渡す。

**full ICU が必要。** `String.prototype.normalize` は full ICU データを要する。
公式の Node.js ビルドに加え、Chromium と workerd も満たす — CI のブラウザ/Workers
ジョブが NFKC の畳み込みを実際に assert しているので、ICU 欠落のランタイムなら
黙って別のキーを出すのではなくジョブが落ちる。`--with-intl=small-icu`(や `none`)で
ビルドされた Node では正しく正規化されないので、その場合は
`unicodeNormalize: false` を使う。

**スループット。** 短い氏名で `toMatchingKey` およそ 50〜70 万回/秒(10万件で
約150〜210ms、計測した複数マシン、Node 22)。約束ではなくオーダーの目安として
扱ってほしい。呼び出しをまたぐキャッシュは意図的に持たない(隠れたグローバル
状態になるため)。数百万行を処理してさらに速度が必要なら、呼び出し側で文字単位に
メモ化してほしい。

**CI がカバーしていない範囲。** Node 18/20/22・headless Chromium・workerd 以外の
ランタイム、とくに Deno・Bun・Chromium 以外のブラウザ。バンドルにエンジン固有の
要素は無いが、それは推論であって証拠ではないため未検証として扱ってほしい。

## API リファレンス

### `reduce(char): ReduceResult`

1文字(異体字セレクタが後続する場合は基底文字+セレクタの1単位)を受け取り、
記録されている JIS X 0213 表現可能な候補すべてを、根拠区分(`basis`)付きで
返す。

`char` が文字列でない場合、またはちょうど1単位でない場合は `TypeError` を
投げる。意図的な仕様で、長い文字列の先頭だけを黙って処理したり、名前の配列を
1つの名前のように受理したりすると、もっともらしい誤出力として不具合が隠れる
ため。異体字セレクタが2つ以上付いた入力も同じ理由で拒否する(1つ目だけを
使えば残りを捨てることになる)。文字列全体には `toMatchingKey` を使う。

`unique` は代表字の一意選択結果で、候補がゼロの場合、または選択ヒューリス
ティックの全段階を経てもなお複数候補が拮抗し一意選択が恣意的になる場合は
`null` を返す。選択ヒューリスティックは次の優先順位: まず法務省告示582号
別表第四に記録された順位を優先し、次に戸籍法関連通達のホップ数が最小のもの
を優先し、それでも決まらなければ、拮抗した候補のうち 常用漢字 であるものが
ちょうど1つならそれを、常用漢字が1つも無ければ 人名用漢字 であるものが
ちょうど1つならそれを(それも複数あれば JIS水準が最小のものを、最小のものが
複数あれば決められない)優先し、それでも決まらなければ(コードポイント順など)
恣意的に選ばず `null` を返す。順位/ホップの段で拮抗する 806 のテーブル
キーのうち、この最後の段が 502 件を新たに解決する。残る 304 件は拮抗した
候補のなかに常用漢字/人名用漢字が(該当する水準で)1つも無いため、`null` の
ままとなる。

順位とホップ数を使う段は
[`src/reduce.ts`](./src/reduce.ts) に記載した独自のヒューリスティックであ
り、他ツールのアルゴリズムを移植したものではない。**常用漢字/人名用漢字の
段は独自ではない**: これは IPA 自身のリファレンス実装が、自らの順位/ホップ
相当の段を使い切ったあとに適用するのと同じ規則を、そのまま(発明せずに)
使っている。この段を支えるのは、リファレンス実装が参照するのと同じ
常用漢字/人名用漢字の政策リストから構築した 2,999 件のテーブル(常用漢字
2,136字・人名用漢字 863字)である。MJ 自身は一意選択の方法を定めていない。
公式の説明は「縮退先の候補が複数示されている文字については、その文字が
使われている状況を勘案し、実際の縮退先を判断する」であり、「常用漢字に
属するもの」「JISコードの最も若いもの」といった規則は**例として挙げられて
いるだけ**である。順位とホップ数を使うのは本パッケージによるデータの読み
方であり、常用漢字/人名用漢字の段はリファレンス実装の読み方である。

IPA は一意選択のリファレンス実装を公開しており
([mandel59/mj2jisx0213](https://github.com/mandel59/mj2jisx0213)、MIT、
© 2015 IPA)、**本パッケージとまだ異なっているのは段の順序だけで、タイブ
レークの規則そのものはもう違いではない**。リファレンスは JIS包摂規準が
あればまずそれを採り、次に戸籍法関連通達(ホップ数順)、法務省告示582号
の順位は**最後**に置いたうえで、本パッケージがいま使っているのと同じ
常用漢字 → 人名用漢字(JIS水準順)のタイブレークに落ちる。本パッケージは
法務省告示582号の順位を最初に、JIS包摂規準を最後に置く。差は目的の違いから
来る: リファレンスは JIS X 0213 への変換表を作るので「既に表現可能」で話が
終わるが、本パッケージは名寄せキーを作るので 㐂 を 喜 に畳むことこそが
目的になる。同梱テーブルで実測すると、順位をホップ数より先に置く(リファレン
スとは逆の)結果、248 の縮退元で別の勝者になり、順位側が常により一般的な
字を選ぶわけではない(㓮 では順位側が稀な 雕 を、ホップ側が日常的な 彫 を選ぶ)。
リファレンスの段の順序が必要ならリファレンスを使うこと。

`unique` をそのままキーに使う前に知っておくべき帰結が2つある:

- **`unique` は CJK 互換漢字になりうる**(該当する縮退元は 165 文字)。
  互換漢字は NFKC で安定しない: `reduce("楳").unique` は U+FA44 で、
  NFKC では U+6885 梅 になる。`toMatchingKey` はホップ毎に正規化するので
  キーには影響しないが、`unique` から自前でキーを作るなら正規化すること
- **MJ が「縮退不要」と言っている字でも置き換わる。** JIS包摂規準・UCS統合
  規則の候補はたいていその文字自身であり、これは MJ の「既に表現可能」という
  表明である。この候補は順位もホップ数も持たないため上の順位/ホップの段では
  決して勝たず、たいていは常用漢字/人名用漢字の身分も自分では持たない。
  結果 1,288 文字では実際に畳まれ(`reduce("㐂").unique` は 喜、
  `reduce("㠀").unique` は 島)、名寄せには有用だが、`unique` は
  「この字形の JIS X 0213 表現」ではないということでもある。
  さらに 5 文字では常用漢字/人名用漢字の段を経てもなお候補が拮抗して
  `unique` が `null` になる

`resolvedVia` は、どのテーブルエントリが引けたかを示す: 入力自身の変異
シーケンスが見つかれば `"ivs"` / `"svs"`、素の基底文字にフォールバックした
(またはセレクタが無かった)場合は `"base"`、何も見つからなければ `"none"`。
IVS 固有の結果とフォールバックを区別できる唯一の手段。

なお `reduce` は関係を**1段階だけ**進める。安定する字に達するまで複数段階を
要する文字が多いため、名寄せキーには不動点まで反復する `toMatchingKey` を使う。

### `isVariant(a, b, options?): boolean`

`a` と `b` が MJ の異体字グラフ上で直接連結しているかを判定する: 一方が他
方に縮退する関係、または両者が同一 MJ 字形の縮退候補同士である場合に true
を返す。これは**直接関係**であり、グラフ全体の推移閉包ではない。一部の根拠
区分(辞書類、読み・字形による類推)は連鎖して大きな連結成分を作るため、推
移閉包にすると本来別の文字同士を過剰に同一視してしまう。実測した連結成分の
規模は [`docs/phase0-report.md`](./docs/phase0-report.md) #6 を参照。

同じ文字同士は `false` を返す。「**異なる**2文字が異体字関係か」を答える関数
なので、同一性も含めて判定したい場合は `a === b || isVariant(a, b)` と書く。

#### `includeInferred` —— 再現率を取るか適合率を取るか

`{ includeInferred?: boolean }`(既定 `true`)。推論エッジ(下の
`getVariants` を参照)は、2字が同一 MJ 字形の候補であることだけで結ばれた
約10%のエッジ。`getVariants` はそれを1件ごとにフラグで返せるが、真偽値を
返す `isVariant` にはそれができないので、代わりにオプションを取る。

```ts
isVariant("井", "牛");                            // true —— どちらも第三の字の代替
isVariant("井", "牛", { includeInferred: false }); // false
```

**既定を `true` にしているのは、厳しい側にすると偽陽性だけでなく本物の
異体字対も落ちるため。** MJ は**縮退が必要な字にしか**縮退関係を記録しないので、
両方が既に JIS X 0213 にある2字の間には記録されたエッジが存在せず、
共候補であることだけが唯一の繋がりになる。新字体/旧字体の対の多くがこの形をしている:

```ts
// 既定ではすべて true、{ includeInferred: false } ではすべて false
isVariant("猫", "貓");
isVariant("摂", "攝");
isVariant("併", "倂");
isVariant("靱", "靭");
isVariant("桝", "枡");
```

**ここで `isVariant` が `true` を返しても、`toMatchingKey` のキーが揃うとは
限らない。** 猫 と 貓 はどちらもすでに不動点(自分自身に縮退する文字)なので、
`toMatchingKey("猫").key` は `"猫"`、`toMatchingKey("貓").key` は `"貓"` の
まま——2つの異なるキーになる。これは上の `reduce`/`toMatchingKey` の役割
分担と同じ非対称が一段上で起きているだけ: `isVariant` は直接関係を報告し、
`toMatchingKey` は縮退の行き先を報告する。共候補であることは前者を成立させ
るが、`toMatchingKey` が辿れるホップは与えない。設計どおりの挙動であって
不具合ではない——MJ は縮退が必要な字にしか縮退関係を記録せず、猫 も 貓 も
その必要が無い字だから。

推論エッジしか持たない文字は 34 文字あり、厳しい側にするとこれらは異体字が
1つも無くなる。記録された関係はどちらでも無傷である(沢―澤、辺―邊、斉―齊、
竜―龍、桜―櫻、国―國、髙―高、﨑―崎 はどちらも `true`)。

この 3,000 件の推論エッジのうち、**1,427 件(47.6%)は
`basis: ["moj-notice-582-appendix-4"]` 単独**——上の
`isVariant("井", "牛")` と同じ型で、告示582号が第三の(より希少な)字の
候補どうしを順位付けしているだけであり、2字自身についての言明ではない。
この層からサンプルを取って調べたところ、妥当な異体字対は見つからなかった
(全数確認はしていないので、あくまでサンプル調査の結果として扱ってほしい)。

3,000 件全部か0件かの二択である必要はない: `getVariants` が返す情報だけで、
この層だけを落とせる:

```ts
function dropNotice582OnlyLayer(char: string) {
  return getVariants(char).filter(
    (v) => !(v.inferred && v.basis.length === 1 && v.basis[0] === "moj-notice-582-appendix-4"),
  );
}

dropNotice582OnlyLayer("井").map((v) => v.char); // ["㐄", "㐩"] —— 牛 が落ちる
dropNotice582OnlyLayer("猫").map((v) => v.char); // ["貓"] —— 残る: basis に family-register-notice も含むため
```

上に挙げた対はどれも影響を受けない——`basis` には告示582と並んで常に
`jis-inclusion-rule` と `family-register-notice` が入っているため、
`basis.length === 1` の条件に当たらない。これは `includeInferred` の2値の
中間に位置する: `true` は推論エッジ 3,000 件を全部残し、`false` は(上の
本物の対も含めて)全部落とすが、この絞り込みはサンプル調査で妥当な対が
見つからなかった層だけを落とす——`getVariants` が返すデータから今すぐ
組める中間の強さの選択肢。

一致が「誰かが責任を問われうる主張」になる場面では `false` を、
検索を広げたいだけなら既定を使うとよい。

### `getVariants(char): Variant[]`

`char` と直接関係にある文字を根拠付きですべて列挙する(直接関係の定義は
`isVariant` と同じ)。順序に意味はない。検索クエリ展開(「崎」で「﨑」も
ヒットさせる)などに使う。

**`basis` を「その機関がこの2字について述べたこと」として引用する前に
`inferred` を確認すること。** グラフのエッジの約10%(30,653件中3,000件)は、
両字が同一 MJ 字形の候補であることからの**推論**でしかなく、その場合 `basis` は
2字の関係ではなく「共有する MJ 字形との関係」を表している。法務省告示582号は
「齍 は 斉 または 資 と書ける」と述べており、斉 と 資 は 齍 を**介して**関係する
だけで、告示は両者が交換可能とは言っていない。したがって `getVariants("斉")` は
資 を `inferred: true` で返し、告示が実際に名指ししている 齍 は
`inferred: false` で返す。

### `toMatchingKey(text, options?): { key, normalized, unresolved }`

`text` の各文字を、自分自身に縮退する安定した代表字に達するまで**繰り返し**
縮退して名寄せキーを生成する(1段階では足りない文字が大半のため)。解決でき
なかった文字は `key` 中で元の文字のまま残し、`unresolved` に記録する。
黙って推測することはしない。

**空白はキーから落とす。** 姓名の間に空白を入れるかどうかは人物の属性ではないので、
`渡辺太郎` と `渡辺 太郎` は同じ `"渡辺太郎"` になる。全角空白・タブ・改行・
2つ以上の連続・前後の空白も同様。目に見えない書式文字（ゼロ幅スペース、BOM、
ソフトハイフン、双方向制御 = Unicode の `Cf`）も一緒に落とす。実運用で効くのは
むしろこちらで、**画面上は同一に見えるのに一致しない**うえ、画面には理由が何も出ない。
異体字セレクタは `Cf` ではなく `Mn` なので触らない。

人名ではなく空白に意味がある入力なら `ignoreWhitespace: false` を渡す。
`normalized` はどちらの場合も空白を保つので、`unresolved[].index` はそのまま使える。

**意図して畳まないもの:** `・` などの区切り記号（ジョン・スミスのように名前の一部）、
`ー` と `―`、ひらがなとカタカナ。いずれも文字列の意味そのものが変わるため、
同じだと決めるのは呼び出し側の判断に残してある。

```ts
toMatchingKey("渡邉 太郎").key;                              // "渡辺太郎"
toMatchingKey("渡邉太郎").key;                               // "渡辺太郎"  同じ
toMatchingKey("渡邉 太郎", { ignoreWhitespace: false }).key; // "渡辺 太郎"
```

**`unresolved[].index` は `normalized` 上の位置であり、渡した入力文字列の
位置ではない。** 正規化は長さを変えるので、このオフセットは入力の末尾を
超えることがある。`normalized` を slice すること:

```ts
const r = toMatchingKey("㍿㖒");   // NFKC で ㍿ は 株式会社 に展開される
r.normalized;                      // "株式会社㖒"
r.unresolved[0].index;             // 4 —— 2文字の入力に対して範囲外
r.normalized.slice(4);             // "㖒"  ✓
```

`normalized` は「Unicode 正規化後・MJ 縮退前」の文字列。
`unicodeNormalize: false` のときは入力と一致する。

`reason` は次のいずれか:

| reason | 意味 |
| --- | --- |
| `"no-candidate"` | MJ縮退マップにエントリが存在しない |
| `"ambiguous"` | 候補が拮抗し、**かつ別々の不動点に至る**(連鎖の途中で起きた場合も含む) |
| `"cycle"` | 各段階は一意なのに連鎖が循環して安定しない(例: 址 と 阯 は互いに縮退する) |
| `"unsupported-sequence"` | 変異セレクタが2つ以上付いていたため、縮退せず素通しした |

拮抗=未解決とは限らない。`reduce` は同点の候補から代表字を名指しすることを
拒否する(当て推量になるため)が、名寄せキーで問うべきはもっと狭い
「拮抗した枝は別の場所に行き着くのか?」である。多くの場合は行き着かない。
𡥨 は 㬜 と 晉 で拮抗するが、そのどちらも先へ進むと 晋 に縮退するため
全ての枝が同じ場所に至り、どちらを選んでも結果は変わらないことが**証明できる**。
`toMatchingKey` は全ての拮抗枝をたどり、一致した場合にのみ採用する —
これは当て推量ではなく証明。

順位とホップ数で拮抗するテーブルキー(文字と変異シーケンス)806件のうち、
502件は1段階手前の 常用漢字/人名用漢字 のティアが `reduce` の中で決着させ、
さらに55件がここでの分岐一致によって解決し、残る249件が `"ambiguous"` として
報告される(既定の NFKC での実測)。**渡邉 が 渡辺 と一致する**のはどちらの
経路でも変わらない — これらの仕組みが入る前は 渡邊 だけが一致して 渡邉 は
一致しないという、どちらか一方に倒すより悪い状態だった。

`reduce` を通り抜けた拮抗については、役割分担は従来どおり:
`reduce("𡥨").unique` は `null`(㬜 と 晉 のどちらかを代表字と名指しするのは
当て推量になるため)だが、`toMatchingKey("𡥨").key` は 晋 になる(その
当て推量が不要だと分かるため)。

**`unresolved` に載るのは漢字だけ。** かな・英数字・記号・空白は定義上 MJ
文字集合の対象外であり、これらを載せると本当の情報が埋もれてしまう。実際、
住所1行で34文字中33文字が `unresolved` に載り、`if (result.unresolved.length)`
という自然な呼び出し側チェックがほぼ全入力で発火していた。漢字以外も `key`
には元のまま入る。

`options.unicodeNormalize` の既定値は `"NFKC"`。実装前調査で、CJK互換漢字
474字中460字が NFKC/NFC で統合漢字に分解されることを確認したため、MJ 変換
の前に正規化しておくことでこれらを無料でカバーできる。正規化で吸収されず安
定して残る文字(髙・邊・濵など著名な例を含む)こそが MJ テーブルの担当範
囲となる。`false` を渡すと MJ 側の寄与だけを分離して見ることができ、
`"NFC"` を渡すと互換漢字を区別したまま残せる。

## IVS 対応

MJ文字情報一覧表では、MJ図形名に IVS(異体字セレクタ、U+E0100–U+E01EF)や
SVS が付与されていることが多い(本パッケージのビルドに用いた版では約59,000件
中約11,000件で、生成される変異シーケンスのキーは 9,950 件)。
`reduce`・`isVariant`・`getVariants` はいずれも「基底文字+直後の異体字
セレクタ1つ」を1入力単位として受理する。該当するシーケンスが見つからない場合、
`reduce` は基底文字のエントリにフォールバックし、それを `resolvedVia: "base"`
で報告する。

シーケンス固有のエントリを引くのは `reduce`(と `toMatchingKey`)だけ。
`isVariant` と `getVariants` はセレクタを入力の利便のために受理するが、
参照は基底文字単位で行う——異体字グラフは文字単位で記録されているため、
`getVariants("辻\u{E0100}")` は `getVariants("辻")` と等しく、基底を共有する
2つのシーケンスは `isVariant` にとって同じ文字になる(したがって自分自身と
同様に `false` を返す)。

SVS(標準異体字セレクタ)として受理するのは **U+FE00–U+FE0D のみ**。
U+FE0E と U+FE0F は Unicode が定める「テキスト/絵文字の**表示**セレクタ」で
あって異体字セレクタではなく、とりわけ U+FE0F は絵文字の一部として通常の
文章に頻出する。これを異体字セレクタとして扱うと黙って食い潰すことになる。
範囲を狭めても失うものは無い: MJ データが実際に使う SVS は U+FE00 と U+FE01
だけである。したがって `toMatchingKey("㊗️")` は U+FE0F を保持する。

副作用として知っておいてほしい点: U+FE0F が異体字セレクタでなくなったため、
`"崎️"` は1単位ではなく2文字になる。したがって単一文字を扱う関数
(`reduce`・`isVariant`・`getVariants`)は、これを黙って 崎 として扱わずに
例外を投げる。`toMatchingKey` は通常どおり処理する。

## ロードマップ / v1 非対応

### 検討中

機能一覧からではなく、実際の名寄せデータが要求するものから拾っている。いずれも
**既定でやらなかった理由**まで書いてあるので、**必要ならイシューでそう言ってほしい**。
実装するかどうかと既定値を決めるのは、実際の利用場面のほう。

- [区切り記号（`・`・`,`・`/`）を畳む](https://github.com/tomatomerde/itaiji-normalize/issues/61)
  — あるデータでは区切りで、別のデータでは名前の一部（ジョン・スミス）
- [かなの統一と長音記号のゆれ](https://github.com/tomatomerde/itaiji-normalize/issues/62)
  — 読み列向けのひらがな ⇄ カタカナ、`ー` と `―`
- [一括名寄せ用のグルーピング補助](https://github.com/tomatomerde/itaiji-normalize/issues/63)
  — ループ自体は短いが、未解決の行の扱いはそうではない
- [ブラウザ向けのバンドル削減](https://github.com/tomatomerde/itaiji-normalize/issues/64)
  — 関数1つで gzip 約282KB は、入力フォームでは現実的な反対理由になる

いずれも**オプトインで既定はオフ**にする。決められないものは決めずに報告する、
というこのライブラリの性質はどれでも変わらない。

他にあれば [イシューを立ててほしい](https://github.com/tomatomerde/itaiji-normalize/issues/new?template=feature_request.yml)。
**実データを数行**添えてもらえると、それが判断材料になる。

### 予定に無いもの

- ホスト型 API・Web サービス化はしない(あくまでライブラリ)
- 法務省の誤字俗字・正字一覧(民一2842号通達別表)は統合しない —
  `docs/phase0-report.md` #4 参照。この調査を行った環境にはネットワークア
  クセスがなく、機械可読性を確認できていない
- テーブルは素の JSON。コンパクトな再符号化(縮退先の共有辞書化、コード
  ポイント差分符号化)により API 全体のバンドルを現在の約 568 KB(gzip)から
  大きく下げられる。実装前調査で設計済み・未実装
- Deno / Bun は CI 未カバー(Node・Chromium・workerd はカバー済み)
- Python版は未着手(TypeScript版の反応を見てから判断)
