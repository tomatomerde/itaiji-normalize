## 0. データ入手の経緯

原本2ファイルは、公式ページから手動でダウンロードしたものを取り込んだ
(調査に使った作業環境から moji.or.jp / moj.go.jp へ直接接続できなかったため)。
SHA-256 を `data/snapshot/PROVENANCE.md` に記録済み(公式配布物との照合は人間作業として残る)。

| ファイル | バージョン | SHA-256(先頭8桁) |
|---|---|---|
| MJShrinkMap.1.2.0.json | 1.2.0 (2018-01-26) | 275b57ec |
| mji.00602.xlsx(MJ文字情報一覧表) | Ver.006.02 | f79075bf |

**構造上の重要な発見**: MJ縮退マップは変換元文字を `MJ文字図形名`(MJ000001等)でのみ識別し、
**変換元の UCS・IVS を一切含まない**(ファイル内に IVS 出現 0 件)。Unicode 文字列を入力に取るには
MJ文字情報一覧表(MJ図形名↔UCS/IVS 対応)の併用が必須。このため同梱スナップショットは2ファイル構成とする。
縮退マップ 1.2.0 の対応版は一覧表 Ver.005.02 だが、MJ図形名は版間で安定な識別子のため
最新の Ver.006.02 を使用(縮退候補を持つ MJ 字で UCS 解決不能になったものは 0 件)。

## 3. 既存 OSS(npm itaiji 1,404 エントリ)とのカバー率(中止基準2: 非該当、ただし書きあり)

itaiji の辞書は `旧字→新字` の単純 1,404 組(根拠情報なし・IVS 非対応)。双方向突合の結果:

**MJ → itaiji 方向(itaiji を再現できるか)**

- 直接縮退(旧字の縮退候補に新字が含まれる): **1,046 / 1,404 = 74.5%**
- 等価クラス(異体字グラフの同一連結成分): **1,209 / 1,404 = 86.1%**
- 未カバー 195 組の内訳:
  - 112 組: 旧字側が MJ グラフに不在。サンプル(龟, 鱼, 桥, 勥, 竻, 匑 …)の大半は**中国簡体字**で、
    日本の行政文字集合を根拠とする MJ の対象外(= データの信頼性の差であり欠陥ではない)
  - 83 組: 両字とも JIS X 0213 内の新旧字体ペア(頸→頚、諫→諌、巖→巌 等)で MJ が接続しないもの

**itaiji → MJ 方向(MJ の独自性)**

- MJ 由来の非自明対応(源字≠縮退先): **27,950 組**(源字 30,313 字)
- うち itaiji に存在するのは 1,046 組 → **MJ 独自対応 26,904 組(itaiji 全体の約 19 倍)**
- 加えて全対応に根拠種別が付き、IVS キー 9,882 件は itaiji に概念ごと存在しない

**判定**: 対応数(19倍)・根拠・IVS で優位性は数値で示せた。**ただし**、MJ 縮退は
「JIS X 0213 で表現可能な字への縮退」であり「新字体への正規化」ではない。啞→唖、鷗→鴎 のように
両字が JIS 内にある新旧字体ペア(itaiji の 246 組)は縮退では変換されない(啞は既に JIS 内なので
縮退先は啞自身)。名寄せ用途では等価クラス判定で 86.1% を同一視できるが、
**「旧字→新字の一方向置換器」としては itaiji の完全上位互換ではない**。README にこの位置づけを明記する。

## 5. Unicode 正規化との関係(実測)

- CJK 互換漢字ブロック(U+F900–FAD9)474 字中 **460 字は NFC/NFKC で統合漢字に分解**される
  (例: 神 U+FA19 → 神 U+795E)。残り **14 字(﨑 U+FA11 を含む)は分解されない**
- 髙 U+9AD9・邊 U+908A・濵 U+6FF5 等の統合漢字の異体は NFC/NFKC で**不変**(正規化では吸収不能)
- IVS(異体字セレクタ)は NFC/NFKC で**保存**される(除去も解釈もされない)

**API 方針**:

- `reduce` / `getVariants` / `isVariant` は **Unicode 正規化を行わない**(入力を尊重。
  互換漢字も MJ テーブルで直接引ける。正規化は情報を破壊するため暗黙に行わない)
- `toMatchingKey` の `unicodeNormalize` 既定は **"NFKC"**(全角/半角・互換文字の折り畳みが
  名寄せに有効)。`"NFC"` / `false` も選択可。既定値と理由を README に明記

## 6. API 最終案(RFP §4 叩き台からの修正提案)

RFP の 4 関数構成は維持。修正・具体化する点:

1. **`isVariant(a, b)` は直接関係で判定**(同一 MJ 字の縮退候補同士、または縮退元→縮退先の関係)。
   推移閉包は辞書類関連字の連鎖により最大 207 ノードの連結成分が生じ過剰統合するため既定にしない
2. **`getVariants(char)` は双方向列挙**: char の縮退先 + char を縮退先とする字を根拠付きで返す
   (逆引きは「列挙」であり一意選択ではないので非対応範囲の reverse() には当たらない)
3. **IVS 入力**: `基底文字+VS` の並びを 1 単位として解釈。IVS キー(9,882)で引けない場合は
   基底文字の UCS キー(30,313)にフォールバックし、どちらで解決したかをフラグで返す
4. **`reduce().unique`** は mandel59/mj2jisx0213(MIT)の一意選択アルゴリズムを参照移植し、
   アルゴリズムと限界(選択不能 → null)をドキュメント化
5. 根拠(basis)は 5 種別の文字列リテラル型 + 詳細(告示の表/順位、通達のホップ数等)を保持

## 7. データパイプライン設計案

```
data/snapshot/ (原本2点 + PROVENANCE.md)          ← ネットワーク取得なし
  → scripts/extract-mji.py     (xlsx → TSV。Python stdlib のみ)
  → scripts/build-tables.ts    (縮退マップ + TSV → コンパクトテーブル生成)
  → src/generated/tables.ts    (文字列リテラル埋め込み。依存ゼロ・全ランタイム対応)
```

マップ更新時は snapshot 差し替え → 再生成のみ。生成結果はコミットしてビルド再現性を保証する。
