# デモページ

ブラウザだけで動くデモの元ファイル。`.github/workflows/pages.yml` が
build → ブラウザ検証 → GitHub Pages へのデプロイまでを行う。
公開先は `https://tomatomerde.github.io/itaiji-normalize/`。

> **まだ公開されていない（2026-08-16）。** リポジトリの Pages が有効になっていないため
> deploy ジョブだけが落ちる。有効化はワークフローからはできない（サイトの作成には
> admin 権限が要る）。手順は `NOTES.md` の「人間の操作待ちの項目」。

## 手元で動かす

```sh
./demo/build.sh          # demo/_site を組み立てる（レジストリから公開版を取得する）
npm run test:demo        # 組み立てた _site を実際の Chromium で検証する
npx serve demo/_site     # 目で見たいとき（http で配る必要がある。ESM は file: で動かない）
```

`demo/_site` は生成物なので commit しない（`.gitignore` 済み）。

## 決めたことと、覆すときにどこを触るか

| 決定 | 理由 | 覆すとき |
| --- | --- | --- |
| **npm 公開版を固定して読み込む**（このリポジトリのソースをビルドしない） | 訪問者が `npm install` して得るものと、ページで見えるものを一致させるため。作業中のツリーを載せると、まだ誰も入手できない挙動を宣伝することになる | `demo/pinned-version.txt` |
| **バージョンをページに表示する** | 上と同じ理由。どの版の挙動を見ているのかが分からないデモは根拠にならない | `build.sh` の `__ITAIJI_VERSION__` 置換 |
| **外部リクエストをゼロにする**（Web フォント・CDN・解析タグを一切使わない） | 「入力はブラウザの外に出ない」と書く以上、フォント1つでも外から取ればその主張が嘘になる。解析タグを入れない判断も同じ | `demo/style.css`（フォント指定）と `demo/index.html` |
| **ページの言語は日本語** | 異体字の名寄せを必要とするのは日本語の氏名・住所データを扱う人で、流入も日本語の記事から来る。README を英語基準にしている方針とは、読み手が違うので衝突しない | `demo/index.html`（英語版を足すなら別ファイルにして相互リンク） |
| **成功例だけでなく失敗例を初期表示に入れる** | このライブラリの主張は「決められないときは決めない」なので、成功例しか出ないデモは説明として不正解になる | `demo/app.js` の `PRESET_TEXTS[0]` |

## リリースのたびに要る作業

新しいバージョンを publish したら **`demo/pinned-version.txt` を上げる**。
上げないとページは古い版の挙動を見せ続ける。忘れても静かに壊れるだけなので、
`build.sh` はレジストリの `latest` と食い違うときに warning を出す
（`docs/releasing.md` にも手順として書いてある）。

## なぜ検証をワークフローに入れてあるか

ページは訪問者に2つ約束している——**何も打たなくても結果が見える**ことと、
**読み込み後は何を入力してもリクエストが発生しない**こと。どちらも本物のエンジンでしか
確かめられないので、`scripts/verify-demo.mjs` が Chromium で実際に操作して検証し、
デプロイはその後にしか進まない。約束を書いたページを、約束を確かめずに配らないため。
